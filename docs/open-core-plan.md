# Data-Khaos Open-Core 开放核心模式规划

> 目的：定义 Data-Khaos 的「开源社区版 + 商业企业版」双版本策略，明确版本边界、代码治理、防白嫖机制与后续开发维护规范。
>
> 核心理念：**核心开源、增值收费**——把基础可用能力开源聚拢生态，把企业级高价值能力（安全合规、身份集成、高级分析、OEM）闭源收费，形成"既开源又不被白嫖"的商业闭环。

---

## 1. Open-Core 模式概述

### 1.1 什么是 Open-Core
Open-Core（开放核心）是企业级开源软件的主流商业模式：**开源核心代码库 + 闭源增值产品**。

- **开源社区版**：代码公开、可自由下载/部署/研究/二次开发，用于吸引开发者、积累社区、建立信任。
- **商业企业版**：闭源收费，提供企业刚需但难以自建的能力（安全、合规、集成、服务），是收入来源。

> 参考对标：GitLab(CE/EE)、Grafana(OSS/Enterprise)、MongoDB、ClickHouse、Superset(核心开源)、Metabase(开源 + 收费版)。

### 1.2 为什么选 Open-Core（目标）
| 目标 | 说明 |
|---|---|
| 避免白嫖 | 把"硬门槛"（合规审计、SSO、细粒度安全、OEM）放在企业版，社区版只给基础，企业无法零成本拿走全部价值 |
| 聚拢生态 | 开源吸引开发者提交 PR、反馈 issue、贡献 connector，降低研发成本 |
| 建立信任 | 公开代码让企业敢用，降低采购决策门槛 |
| 形成收入 | 企业版 + 技术支持 + OEM 绑定，支撑产品持续迭代 |

## 2. 版本边界：社区版 / 企业版功能矩阵

> 划分原则：**凡是"安全、合规、集成、规模化、服务"相关的一律进企业版**；凡是"单机可用、基础建模、基础可视化"留在社区版。

| 维度 | 开源社区版（公开） | 商业企业版（闭源收费） |
|---|---|---|
| **可视化** | 拖拽画布、图表卡片、基础仪表板、嵌套分析板 | 高级可视化模板、大屏模板库、主题定制 |
| **身份集成** | 本地账号登录、基础角色权限 | SSO、LDAP、OIDC、CAS、SAML 身份集成、双因素认证(2FA) |
| **数据源** | MySQL、API、JSON 基础数据源 | 高级数据源（Oracle/达梦/星环/ClickHouse 等）、数据脱敏、高级连接池 |
| **权限** | 用户登录、基础角色权限 | 细粒度 RBAC、行级/列级数据权限、数据遮蔽、审批流自动化授权 |
| **分享导出** | 看板分享、导出图片/PDF | 计划推送、多格式导出、iframe 嵌入鉴权 |
| **审计合规** | 基础操作日志 | 完整审计日志、操作追溯、合规报表、审计导出 |
| **AI 能力** | 基础 AI 辅助生成图表 | AI-Agent 深度分析、批量自然语言分析、智能洞察 |
| **服务平台** | 社区 Issue 交流、自部署 | 技术支持、部署协助、白标贴牌 OEM、SLA 保障 |

> 注：上表为**当前规划**，随产品演进可持续把社区能力上移为企业版能力（见 §5.3 能力上移策略）。

## 3. 代码仓库与模块治理策略

> 目标：**从代码结构上保证企业版不泄露、社区版可独立构建**。

### 3.1 仓库策略（推荐：双仓库）
| 仓库 | 内容 | 可见性 |
|---|---|---|
| `Data-Khaos`（主仓库） | `common/gateway/auth/permission-business/permission-api/datasource(datasource-api)/metadata/mart(mart-api)/query/visual/schedule/notification/approval` + `data-khaos-web` | 公开（开源） |
| `Data-Khaos-Enterprise`（私有仓库） | 企业版模块：`auth-enterprise(SSO/LDAP/OIDC)`、`security-enterprise(RBAC高级/脱敏/审计)`、`ai-agent-enterprise`、`connector-enterprise(高级数据源)`、`oem(白标)` | 私有（仅授权） |

### 3.2 模块隔离原则
- **社区/企业代码物理分离**：企业版模块放在独立 Maven 模块或独立仓库，**绝不与开源模块混编在同一 jar**。
- **接口契约化**：企业版通过 `*-api` 工程（如 `datasource-api`、`permission-api`）对社区版暴露**接口 + SPO/扩展点**，社区版只依赖接口，不依赖企业实现。
- **前端动态加载**：前端菜单/路由按能力位动态渲染，企业版页面作为独立 chunk，仅企业版构建产物打包。
- **`*-api` 工程保持公开**：接口、DTO、常量、自动配置公开，保证社区版可编译；**实现类**放私有模块。

### 3.3 一次构建、按 License 启用
- 两个版本可从**同一套源码树**构建，通过 **License 文件 / 启动参数** 控制企业版 Bean 是否生效（类似 Grafana/Metabase 做法）。
- 企业版 jar 不出现在公开仓库，但可通过私有 Maven 仓库 / 离线包分发给授权客户。

## 4. 许可证策略（防白嫖第一道防线）

| 建议 | 说明 |
|---|---|
| 社区版协议 | **Apache-2.0**（宽松、可商用、受企业欢迎）或考虑 **AGPL-3.0**（更强传染性，防止闭源二次售卖） |
| 企业版协议 | 私有商业许可（Commercial License），不开源，授权付费 |
| 商标/品牌 | 保留 `Data-Khaos` 商标，企业版/OEM 需授权，禁止社区版移除版权声明 |
| 版权声明 | 所有文件保留版权头，禁止社区版分发时删除出处 |

> 取舍提示：Apache-2.0 更利于传播但防白嫖弱；AGPL-3.0 防白嫖强但可能吓退部分企业。**建议社区版用 Apache-2.0、企业版用商业许可**，用"功能边界"而非"协议传染"来防白嫖。

## 5. 防白嫖机制（核心设计）

> 防白嫖不是"锁死代码"，而是让企业**自己算账**：自建/改造企业版能力的成本 > 直接付费。

### 5.1 功能壁垒（首选）
- 把企业必需但**自建成本高**的能力闭源：SSO 协议对接、行/列数据权限引擎、完整审计+合规报表、AI-Agent、OEM 白标。
- 社区版保留"能跑通 demo、够用基础"，但**企业规模/合规场景必须升级**。

### 5.2 使用限制（可选）
- 社区版可加**资源上限**（如：看板数、用户数、数据源数、API 调用频率），超出提示升级企业版。
- 导出加**水印/品牌**，企业版去除。

### 5.3 能力上移策略（持续盈利）
- 每 1–2 个版本，选 1–2 项"新成熟能力"从企业版下沉到社区版，制造升级动力与社区好评。
- 同时持续在企业版新增更高级能力（AI-Agent、合规、多租户），保持"高价值永远领先一个身位"。

### 5.4 服务绑定
- 社区版只提供 issue 交流；**部署协助、SLA、技术支持、OEM 授权**一律付费，形成服务收入。

## 6. 后续开发规范（怎么写代码）

> 目标：让"一段代码将来该进社区版还是企业版"有明确判断标准，避免夹带泄露。

### 6.1 新功能放哪边（判断清单）
开发前先回答：
1. 是否涉及**身份集成 / 安全 / 合规 / 审计 / 多租户**？→ 企业版
2. 是否涉及**高级数据源 / 数据脱敏 / 细粒度权限**？→ 企业版
3. 是否**卖点 / 差异化 / 企业付费点**？→ 企业版
4. 是否**基础建模 / 可视化 / 单机可用**？→ 社区版
5. 是否**通用基础设施 / 公共能力**？→ 社区版（公共服务）

### 6.2 提交规范
- 社区/企业代码**分仓库提交**，禁止在企业版 commit 里混入社区版代码依赖私有实现。
- 企业版只依赖 `*-api` 接口，提交前自查：`grep` 确认未 import 企业版私有类到公开模块。
- 社区版 PR 只接受公开模块改动；企业版改动进私有仓库。

### 6.3 架构约束（写进后端开发指南）
- 所有模块面向接口编程，扩展点用 Spring 自动配置(`AutoConfiguration.imports`) + `@ConditionalOnProperty` 实现「同一源码、按 License 启用」。
- 把 `*-api` 接口设计成 SPI，企业版实现注入，社区版可 mock 运行。

## 7. 维护与运营策略

### 7.1 版本策略
| 版本 | 频率 | 说明 |
|---|---|---|
| 社区版 LTS | 半年一次 | 稳定、可长期使用，供社区大版本升级 |
| 社区版 Release | 每月一次 | 迭代新功能、修复、合并 PR |
| 企业版 | 随社区版 + 紧急补丁 | 企业专属功能 + 安全补丁优先 |

### 7.2 版本号
- 维持 `v1.0.0` 语义化版本基线（对齐 `versionPlanning.md`），社区/企业版共用主版本号，企业版附加 `-ent` 后缀或独立 build。

### 7.3 社区维护
- 建立 `CONTRIBUTING.md`：贡献规范、能力位/权限规则（对齐 permission-handbook）、代码风格。
- 维护 `Security` 与 `Bug` 标签，安全漏洞在社区版 **SSVC 优先响应**。
- 定期发布 Changelog、Roadmap，公开能力上移计划。

### 7.4 企业服务
- 企业版提供：部署协助、技术支持、SLA、OEM 白标、专属大客户定制。
- 建立企业版客户支持通道（工单/专属群），与社区 issue 分离。

## 8. 落地路线图（建议）

| 阶段 | 内容 | 产出 |
|---|---|---|
| P0（当前） | 确定许可证、仓库拆分、`*-api` 契约化改造 | 双仓库就绪、社区版可独立构建 |
| P1 | 企业版首个模块落地（建议先从 **SSO 身份集成** 或 **审计合规** 切入，价值最高） | 企业版 MVP、License 启用机制 |
| P2 | 高级数据源 + 数据脱敏 + 细粒度 RBAC 上企业版 | 企业版能力成型 |
| P3 | AI-Agent 深度分析、OEM 白标 | 差异化卖点兑现 |
| 持续 | 能力上移 + 社区运营 + 商业化 | 社区/商业双增长 |

> 建议首个企业版模块切**审计合规**或 **SSO**：前者合规刚需、后者集成刚需，都是企业"不用企业版就做不到"的硬门槛，最能体现防白嫖价值。
